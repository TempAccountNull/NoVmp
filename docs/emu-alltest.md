# emu-alltest — harness options and machine state

`build\x64\Release\tests\emu-alltest.exe` compares Unicorn against the host CPU (hardware cases) or against values derived from the Intel SDM (expected-value cases). Source: `Emulator\tests\alltest\at_main.cpp` (options), `at_cases.hpp` (case-file format), `at_engine.hpp` (how options reach Unicorn).

## Modes

| option | what it runs |
|---|---|
| *(none)* | quick sweep: every 7th instruction form, 2 iterations (test.cmd smoke run) |
| `--full [--iters N]` | every form, N iterations (default 6), report in `--out DIR` |
| `--filter S` / `--sample N` / `--rebuild` | restrict the sweep / sample / re-sweep the opcode space |
| `--cases FILE` | hand-written snippets with a chosen input state; format at the top of `at_cases.hpp` |
| `--expect-only` | with `--cases`: only the expected-value (`=>`) lines — they never run natively |
| `--shard K/N` | with `--cases`: only the K-th of N contiguous blocks of the case lines (U543); the N runs together are the whole file in order, the case numbers restart per block |
| `--bench [--reps N] [--filter S] [--scale F] [--bench-cpu C] [--csv FILE]` | performance benchmark (U500, `at_bench.hpp`): 13 workloads of our own code, Unicorn only — integer/branch, AVX/FMA, SSE integer, x87, REP strings, TLB misses, self-modifying code, 4096 short TBs, code/count/memory-hook overhead, short `uc_emu_start` calls, `uc_open` churn. Cold and warm median of N (default 5) fresh engines, Minsn/s from a calibrated instruction count, and an FNV-1a hash of the complete guest end state that must not change between builds. Pinned to logical CPU C (default 4) at high priority |
| `--profile N` | with `--bench` (per workload) or a quick/`--full` run (whole run): in-process sampling profiler, the N hottest functions self and inclusive (PDBs next to the exe; `[jit]` = TCG-generated code) |
| `--hw-repeat N [--hw-cpu SPEC] [--hw-load N]` | with `--cases`: run-to-run measurement of the hardware cases (U1050), below |
| `--events` | with `--cases`: both engines' event lines for every case (U1741: EFLAGS image RF / TF, DR6, #PF access type), below in "Debug registers and event lines" |

## Machine-state options (apply to `--cases` runs)

These set **real architectural state** defined by the SDM — they are not test tricks. They exist because the snippets run in user mode, where the OS normally owns these registers.

| option | what it sets | why |
|---|---|---|
| `--cpuid FILE` | a CPUID profile (e.g. `Emulator\data\cpuid_i5-13600k.txt`) | Unicorn reports exactly that CPU's CPUID leaves. Since U435 a profile is **strict by default**: features the profile hides raise #UD. U1473: a comment line `#@ microcode REV platform-id N` (REV hex, N 0..7) sets the profile's microcode revision and IA32_PLATFORM_ID (`UC_CTL_X86_MICROCODE`; reported through IA32_BIOS_SIGN_ID / 17H, docs/quirks.md "Microcode update trigger"); the run prints `microcode: revision ...h, platform ID N (profile)`; without the line the model default stays. |
| `--strict` / `--no-strict` | `UC_CTL_X86_CPUID_STRICT` = 1 / 0 | explicit override of the U435 default; `--no-strict` lets hidden features execute (only for testing the profile mechanism). The strict setting also decides the XSAVE enumeration checks made at run time: with a strict profile XGETBV ECX = 1 needs the profile's CPUID.(0DH,1):EAX.XGETBV1 (U1203) and XSETBV accepts an XCR0 bit only if both the model and the profile report the component in CPUID.(0DH,0):EDX:EAX (U1220, user decision 2026-10-10), and the compacted form of XRSTOR needs the profile's CPUID.(0DH,1):EAX.XSAVEC, else #GP(0) (U1221); and only a strict profile narrows the reset XCR0 to its leaf 0DH (also when it is installed, or strict mode switched on, after the engine started; U1225, user decision 2026-10-11); with a non-strict profile these follow the model alone (XSETBV: the model's own components, whatever the profile reports; the reset XCR0: the model's value). The control is a CPUID reporting policy, not a reinitialisation of guest state: switching strict off after the engine started keeps XCR0 exactly - the components it un-hides need a valid XSETBV (or `--xcr0`) first (U1441, user decision A19 2026-10-14). A strict profile also decides which CR4 bits exist (U1680, plan 1.J.61): a CR4 bit whose CPUID bit the profile hides is reserved - MOV to CR4 #GP(0), absent from IA32_VMX_CR4_FIXED1 and from the reset CR4 (`--guest` / `--vm` 00050600H: no SMXE / KL / UINTR / LA57; `--host` 000D0600H: no UINTR / LA57; the model alone 020D0600H) - `docs/quirks.md` "CR4 at engine start". It also decides which IA32_EFER bits WRMSR may set (U1780, plan 1.J.63): SCE / NXE / SVME / FFXSR need the profile's CPUID.80000001H:EDX.SYSCALL / EDX.NX / ECX.SVM / EDX.FFXSR besides the model's, else WRMSR #GP(0) (SDM 334569-093 Vol2D WRMSR p. 6-9); both i5-13600K profiles report SVM = 0 and FFXSR = 0, so EFER.SVME is reserved under `--host` / `--guest` / `--vm` also with `--apx` (no VMX model there; before U1780 the MAX model's SVM bit made it writable); a strict profile installed after the engine started drops such bits from IA32_EFER, and one that hides SYSCALL leaves SCE out of the 64-bit reset value (suites `efer_prof_*`). |
| `--xcr0 V` | XCR0 (written with `uc_reg_write`) for both kinds of case | XCR0 is the OS-set register (XSETBV) that enables x87/SSE/AVX/AVX-512/AMX state; it decides whether AVX/AVX-512/AMX instructions run or #UD. Not given (or 0) = automatic (U540, below). Needed only to test the XCR0 gating itself (a component *disabled*, e.g. AVX state off → VEX #UD). |
| `--cr0 V` | CR0 for both kinds of case | Not given (or 0) = automatic (U540, below). PG must stay clear (Unicorn memory is flat). CR0.TS (bit 3) acts on the snippet only (U1200, below). |
| `--avx512` | `UC_CTL_X86_AVX512` = F\|DQ\|BW\|VL\|CD\|IFMA\|VPOPCNTDQ\|BITALG\|VBMI\|FP16 before the engine starts | AVX-512 is opt-in (off in MAX and in the i5-13600K profile, which has none). |
| `--xeonphi` | adds `UC_X86_AVX512_4VNNIW`\|`4FMAPS`\|`ER`\|`PF`\|`PREFETCHWT1` (AVX512F implied) to the `UC_CTL_X86_AVX512` mask (U990) | The Intel Xeon Phi-only families (SDM 092 Vol2D chapter 8) are opt-in on top of AVX-512; `--avx512` alone leaves them off (`Emulator\data\cases_xeonphi.txt` / `cases_xeonphi_off.txt`). |
| `--amx` | `UC_CTL_X86_AMX` = all AMX parts | AMX is opt-in. |
| `--amx-tf32` | adds `UC_X86_AMX_TF32` to the `UC_CTL_X86_AMX` mask (U1150) | AMX-TF32 (TMMULTF32PS, ISE 319433-060, withdrawn in -062) is an explicit opt-in that `--amx` (`UC_X86_AMX_ALL`) never includes; unverified (self-contradictory pseudocode, docs/quirks.md); `Emulator\data\cases_amx_tf32.txt` runs with `--amx --amx-tf32`. |
| `--avx10 N` | `UC_CTL_X86_AVX10` = N (1 or 2, optionally \| 0x100 `UC_X86_AVX10_V1_AUX`, \| 0x200 `UC_X86_AVX10_V2_AUX` (U1095); hex accepted, e.g. `--avx10 0x202`) | AVX10 is opt-in; CPUID then also reports AVX, AVX2 and the AVX-512 flags of AVX10.2 spec 361050-007 Table 3.2 / SDM Vol1 Table 16-2 plus AVX512VL (U1096: not in those tables, a hardware / SDE 10.13.1 -dmr based choice); not VP2INTERSECT, not the Xeon Phi bits (U1090). |
| `--apx` | `UC_CTL_X86_APX` = `UC_X86_APX_F` (ledger U610) | Intel APX is opt-in (the i5-13600K has none): CPUID.(7,1):EDX.APX_F, leaf 29H, XSAVE component 19 (R16-R31), REX2. The case keys `r16`..`r31` move R16-R31 like the ZMM/K state (Unicorn only). |
| `--x86-features N` | `UC_CTL_X86_FEATURES` = N before the engine starts (ledger U1181; mask of `UC_X86_FEATURE_*`, hex accepted, e.g. 8 = `UC_X86_FEATURE_LAM`) | Platform features such as TSE, Thread Director, FRED and LAM are opt-in (off in MAX and in the i5-13600K profile). `Emulator\data\cases_lam.txt` runs with `--x86-features 8 --expect-only`. |
| `--xinuse-model p-core` / `--xinuse-model e-core` (and the platform switch) | `UC_CTL_X86_XINUSE_MODEL` (ledgers U1480 / U1481) for the case engines and the quick/`--full` sweep | The XINUSE model of x87 / SSE / AVX (`docs/xinuse.md`): what XGETBV(1) and XSAVE's XSTATE_BV report. Selection: `--xinuse-model` overrides; else `--guest` / `--vm` = P-core model (the VMware guest majority; the guest's physical core is never assumed); `--host` = the verified core type of the CPUs the native runs use (CPUID.1AH and Windows' EfficiencyClass agree on each, all one type, e.g. with `--hw-cpu P` / `E` on bare metal), else the CPUID profile's (07H.0:EDX[15] hybrid = 1 and 1AH 40H / 20H), else the P-core model as a logged fallback; `--AMD` = always in use (the behaviour before U1480, no Intel rule); no switch = not written (the engine default: P-core model on an Intel CPU model). The run prints `xinuse model: <model> (UC_CTL_X86_XINUSE_MODEL n) - <source>` and `xinuse evidence: <profile / host CPU evidence>`. Another value exits with code 2. |
| `--seeded` (default) / `--rdrand-seed N` / `--HostSeed` | `UC_CTL_X86_RDRAND` (ledger U835, decision D8) = `UC_X86_RDRAND_SEEDED` with seed N (default 0) / `UC_X86_RDRAND_HOST`, for the case engines and the quick/`--full` sweep | RDRAND/RDSEED source. Seeded = a deterministic model (SplitMix64 of seed + n * 9E3779B97F4A7C15h, CF = 1), so runs repeat exactly; the seed and the draw count are part of a uc_context. HostSeed = the host CPU's RDRAND/RDSEED (value and CF as the host returns them). Either way a hardware case never sees the host's own draw, so `hwcheck_gate1`'s RDRAND/RDSEED cases stay tagged `# host state: RDRAND/RDSEED values`. The run prints `rdrand: seeded, seed 0x0 (--seeded, the default)` or `rdrand: host DRNG (--HostSeed)` after the machine-state lines. |
| `--host [--host-core P\|E]` / `--guest` / `--vm` / `--AMD` (mutually exclusive; `--vm` = `--guest`; none = defaults) | the CPUID profile (ledger U1491, with its `#@ microcode` line) and `UC_CTL_X86_SMM_REVISION` (ledger U1465), for the case engines and the quick/`--full` sweep: `--host` = `Emulator\data\cpuid_i5-13600k_bare_host.txt` (P-core, the default) or, with `--host-core E`, `cpuid_i5-13600k_bare_host_ecore.txt`, SMM revision 00030101h; `--guest` / `--vm` = `cpuid_i5-13600k.txt` (the VMware guest, the gate profile), 00030004h; `--AMD` and none: no profile, nothing written | U1491 (user requirement 2026-10-15): emulate EITHER the VMware guest OR the bare host, explicitly selected, every CPUID value from a capture of that environment, so a sample's anti-VM / anti-debug checks can be run under both and compared. The bare-host files are generated from the bare-host captures only (`Emulator\tools\bare_host_cpuid.py --write`; suite `bp2_profile_check` re-derives them byte for byte; their headers give the provenance, the P-core vs E-core differences and the representative logical processor, LP 0 / LP 12, whose APIC IDs they carry). `--host-core` only with `--host` (P or E, case-insensitive, once). An explicit `--cpuid FILE` overrides the platform's profile. The run prints `cpuid profile: FILE (SOURCE), N rows` (SOURCE e.g. `--host default: bare host, P-core`, `--host --host-core E default: bare host, E-core`, `--guest default: VMware guest`, `--cpuid, overrides the --host default FILE`) and `cpuid core type: P (CPUID.1AH:EAX[31:24] = 40H Core)` / `E (... 20H Atom)` / `none (07H.0:EDX[15] hybrid = 0 ...)`; without a profile `cpuid profile: none (...)`. Since U1491 the effective profile (also a plain `--cpuid`) and `--strict`/`--no-strict` reach the sweep's Unicorn engines too (without either, the sweep is unchanged). The hardware gate files keep `--cpuid cpuid_i5-13600k.txt` (they run in the VMware guest). The platform profile (physical i5-13600K / VMware guest / AMD) that selects the SMM revision identifier the Intel 64 SMRAM map reports (`docs/smm.md`): `--host` = inferred from indirect coreboot evidence (never read from the processor), `--guest` = the SDM's documented minimum as the default approximation (no VMware source), `--AMD` = the APM value 00030064h of AuthenticAMD CPUs (the engines' CPU model and vendor are not changed). Table 34-1 CPUs keep 00030004h. Chosen explicitly, never from the environment; two different switches exit with code 2. The run prints `platform profile: ...` (profile, revision, classification). The SMM revision has no effect on any test result (no case or sweep form raises an SMI); the CPUID profile has (CPUID values, strict #UD, MAXPHYADDR from 80000008H: 46 bits on the bare host, 45 in the guest). U1660 / U1661 (plan 1.J.59): both i5-13600K profiles report CPUID.01H:ECX.VMX[5] = 1, so a strict profile turns the engine's VMX model on (also a plain `--cpuid FILE`; not with `--no-strict` or `--apx`), and `--host` / `--guest` / `--vm` also write IA32_FEATURE_CONTROL = 5 (lock, VMX outside SMX) before the first instruction - the platform firmware's value (CPU-Z MSR 3AH on every logical processor of both machines, `E:\CPU Info`; evidence, no CPL0 project capture), printed as `platform firmware: IA32_FEATURE_CONTROL = 5 ...`; without a platform switch the MSR keeps its reset value 0 (SDM 093 Vol3C 26.7 p. 26-3). `docs/vmx.md` "Platform profiles". |
| `dr0`..`dr3`, `dr6`, `dr7` (a case's input tokens, ledger U1740) | the debug registers for the snippet: native `SetThreadContext` on the thread that runs it, Unicorn `uc_reg_write` | Instruction / data breakpoints and DR6 from user mode, both engines; section "Debug registers and event lines" below. |
| `dbcount`, `dr6mask=V` (a debug-register case's input tokens, ledger U1771) | `dbcount`: the snippet's first event resumes with DR7 unchanged on both engines (later ones with DR7 = 0) and every #DB of the run is counted; `dr6mask=V`: DR6 is compared only in the bits of V | How many #DBs one instruction boundary gives (D-f: TF and a data breakpoint = one #DB), without comparing DR6 bits the hardware question leaves open (B0-B3 with BS). |

With `cpl=3 cr4.cet=1` the WRUSS lines of `cases_tsx_cet.txt` (U1831) compare untagged; without `cr4.cet=1` Unicorn gives #UD. |

### Automatic machine state (U540, plan 1.H.2)

Without `--xcr0` / `--cr0`, emu-alltest derives the state per kind of case and prints the effective values first (`machine state: hardware cases XCR0=… CR0=…` / `machine state: expected-value cases …`, read back from an engine configured like the run's):

| kind of case | XCR0 | CR0 | why |
|---|---|---|---|
| hardware (no `=>`, compared with this CPU) | the host's XCR0, `_xgetbv(0)` (only when CPUID.1:ECX.OSXSAVE = 1; else Unicorn's reset value) — 7 on the i5-13600K under Windows (x87\|SSE\|AVX; the profile's leaf 0Dh also offers PKRU, bit 9, which Windows leaves off) | 40033h = PE\|MP\|ET\|NE\|AM (U834; 33h before) | the comparison is against this machine, so Unicorn gets this machine's OS-owned state, not a typed number |
| expected-value (`=>`, vs the SDM) | Unicorn's reset value: every state component the CPU model, the opt-ins and the CPUID profile support (`unicorn\qemu\target\i386\cpu.c`, x86_cpu_reset, U120/U370) — e.g. 21Fh (MAX, no opt-in), 2FFh (`--avx512` or `--avx10`), 6021Fh (`--amx`), 7h with the i5-13600K profiles (`--host`, `--host --host-core E`, `--guest` / `--vm` / `--cpuid cpuid_i5-13600k.txt`; U1530: a strict profile's reset XCR0 is the capture's, read from its CPUID.(0DH,0):EBX - Windows' 7h on both machines; 207h before U1530); with such a profile IA32_XSS is also the capture's derived value (900h bare host, 800h guest; U1531) | Unicorn's reset value 11h (PE\|ET) | the SDM model of an OS that enabled everything the CPU has. This XCR0 is an emulator **environment** choice (OS-preconfigured state, like CR4.OSXSAVE, U67), not the architectural RESET value: after power-up / RESET the SDM gives XCR0 = 1H, every other bit 0 (SDM 093 Vol3A 2.6 p. 2-23; Table 12-1 p. 12-3). Per-model component table and rules: `docs/quirks.md` "Emulator environment choices" (U1440) |
| the quick / `--full` sweep | Unicorn's reset value (UC_CPU_X86_MAX, printed with the host's XCR0) | 11h | unchanged (the `--full` baseline) |

**Windows' CR0.** The host's full CR0 is 80050033h (PG\|AM\|WP\|NE\|ET\|MP\|PE), read natively with `smsw rax` (Windows does not enable UMIP on this machine; checked 2026-10-09). PG cannot be set (Unicorn's memory is a flat map without page tables); WP acts only on supervisor writes through paging; AM acts only with RFLAGS.AC = 1 at CPL3: until U834 QEMU raised no alignment-check #AC (EXCP11_ALGN was never raised) and 33h was used; since U834 Unicorn implements #AC and hardware cases get 40033h, so a `cpl=3` case with `rflags=0x40202` faults on a misaligned access on both engines (`cases_ac_hw.txt`). Windows clears RFLAGS.AC while it dispatches a user-mode exception, so when both engines fault emu-alltest takes Unicorn's AC bit for the host too (the other flags and the vector are compared as before). So 33h (+ AM) is the part that acts: NE = 1 makes a pending unmasked x87 exception raise #MF (not FERR#) like the host — `cases_reach.txt` needs it (it ran with `--cr0 0x33` before); MP matters only with CR0.TS = 1 (never set). Every other hardware file gives exactly the same results with 33h as with the reset 11h (U540 check: all 11 hardware case files of test.cmd, case by case).

**What test.cmd passed before U540, and why it could go:** `--xcr0 7` on every hardware file (= the host's XGETBV value; without it the profile's reset XCR0 would be 207h), `--cr0 0x33` on cases_reach (= the new default), `--xcr0 0xE7` on the 17 AVX-512/AVX10 expected-value files and `--xcr0 0x60007` on cases_amx (the reset values 2FFh / 6021Fh additionally enable MPX and PKRU state, which no case uses). All 20 are removed; every file gives exactly the same cases and results (U540 check: old serial test.cmd output vs the new run, case by case).

**When `--xcr0` / `--cr0` are still needed:** to test the XCR0 gating itself (a component disabled) or another CR0 (e.g. NE = 0 → FERR#). They apply to both kinds of case.

**CR0.TS in `--cases` runs (U1200).** With CR0.TS = 1 the thunk itself cannot run: its prologue (FXRSTOR64, VINSERTI128) and epilogue (FXSAVE64, VEXTRACTI128, FNSTENV, FNINIT, ...) are x87 / SSE / AVX instructions, which raise #NM while TS = 1 (SDM 092 Vol3A 2.5, p. 2-17). The `--cases` runner therefore sets `unicorn_engine::ts_hooks`:
- the engine starts with the configured CR0 minus TS (`--cr0 0x10019` is written as 10011h);
- a code hook at the snippet's first instruction sets CR0.TS when the configured CR0 has it;
- a code hook at the epilogue's first instruction clears CR0.TS before the state save, whoever set it (the hook above, or the snippet with MOV CR0 at CPL0). Before U1200 the epilogue of a snippet that set TS raised #NM itself, so such a line reported #NM even when the snippet's own instruction completed (`notes\sdeida\probes\xsave_ts2.log`: a plain `nop` line ended in #NM), and the state was not saved;
- each hook that changes CR0 also writes RIP = its own address: the translator reads CR0.TS when it translates a block (hflags HF_TS_MASK, part of the block key), so Unicorn leaves the current block and translates the next one with the new CR0.TS. The second visit of a hook finds nothing to change.

The machine-state line prints the configured CR0 with "CR0.TS set for the snippet only (U1200)". The flag is set by the `--cases` runner only: the quick / `--full` sweep (CR0 11h) is unchanged. Example (U1201): `Emulator\data\cases_xstate_ts.txt` (`--cr0 0x10019`: XSAVE / XRSTOR / XSAVEOPT #NM, x87 / SSE / AVX #NM, CLTS inside the snippet) and its control `cases_xstate_ts_ctl.txt` (`--cr0 0x10011`, with lines that set TS by MOV CR0).

## test.cmd: selective and parallel runs (U541–U543, plan 1.H.3)

```
test.cmd [--release | --debug] [-j N | --jobs N | --serial] [-v | --verbose] [list | NAME ...]
```

- **NAME** = a group or one suite id; several at once (`test.cmd evex x87`); no NAME (or `all`) = every suite, the full gate. `test.cmd list` prints the groups, the suites and their commands. Unknown names/options: message + usage, exit 2.
- **Groups:** `unit` (Unicorn unit tests + emu-uc72-risk), `sweep` (emu-alltest quick run), `selftest`, `expect` (every expected-value file), `evex`, `amx`, `fp16`, `avx10`, `ext` (Key Locker / SHA-SM / VNNI-IFMA), `sse`, `nan`, `x87`, `hw` (everything compared with the host CPU), `quirks`, `backport`, `tools` (check_decode_dups.py). A suite can be in several groups.
- **Parallel:** the suites are independent processes; up to N run at once (default NUMBER_OF_PROCESSORS, `--serial` = 1), longest first (the previous run's times, `logs\times.tsv`). Each writes its own log `build\x64\<config>\tests\logs\<suite>.log`; after the run each suite's key lines (command, machine state, summary, tags) are printed in suite order, `-v` prints whole logs.
- **Verdicts** are the old test.cmd rules: exit status 0; hardware files (`hw`): `differing: 0` + exit 0 + a strict CPUID profile; `expect_selftest_bad`: `cases: 7, differing: 7` + exit 1 (U772: 7 with the wrong error code). A crash (negative exit status) now fails a suite (the old `if errorlevel 1` let it pass). **Case count (U1841, plan 1.F.13.b):** every `--cases` suite must also print `cases: N` with N = the number of case lines the runner counts in the file itself, with the rule of the host package's `expected_counts.txt` (every line, split at LF with one trailing CR removed, that is not empty and does not start with `#`; `--expect-only`: only the lines containing `=>`; `--shard K/N`: lines T·(K−1)/N .. T·K/N − 1); a line emu-alltest could not run makes N smaller and fails the suite. `harness_selftest_bad` (kind `herr`): every line of `Emulator\data\harness_selftest_bad.txt` is broken on purpose and must be reported as a harness error (`case lines: L, run: 0, harness errors: L`, `cases: 0`, exit 1). ## Random input state (quick / `--full`, U931)

Each iteration of a sweep form starts from a random input state (`at_main.cpp` `rnd_state`): GPRs from a mix of small values, edge values (0, 1, 7Fh, 80h, FFFFh, 7FFFFFFFh, 8000000000000000h, ~0, ...) and full 64-bit values that never alias our regions; RSP / RSI / R14 / RDI the harness pointers; RCX bounded to 0–127; random CF PF AF ZF SF OF, DF one time in 8; MXCSR RC / FTZ|DAZ every 4th iteration; XMM/YMM lanes as integer bytes, floats or doubles (finite values, ±0, ±∞, NaN, denormals, raw bits); x87 registers as finite doubles converted to 80 bits or raw bytes; the 64 KiB operand memory and the test stack random, with 256 bytes of floats/doubles at MEM + 8000h and MEM + 9000h. The generator is xoshiro256** seeded with SplitMix64 from the form's encoding (FNV-1a 64) and the iteration number, so a form's inputs depend only on (form, iteration): `--filter`, `--sample` and the quick run reproduce the `--full` inputs of that form. Before U931 one `std::mt19937_64` (seed 5EED1234h) ran through the whole sweep, one call per random byte (35% of a `--full` run); the shaping rules are unchanged, the random values (and so the per-row CSV details) changed once with U931. The `--cases` files never use this generator (unset state is 0, see `at_cases.hpp`), and neither does `--bench`; RDRAND/RDSEED values come from the separate seeded model (U835, `--seeded`).

**Machine state per iteration (U1124).** The sweep's Unicorn engine is created once per form; since U1124 every iteration starts from the CPU state right after loading the form (a `uc_context` saved then and restored before each run: registers, CPL / CS, control registers, MSRs, the RDRAND draw count), and the memory regions are rewritten as before. Before U1124 iteration n + 1 started from where iteration n left the CPU, so a privileged form that changed CPL or CS (IRET, SYSRET, a far return, ...) ran its later iterations in that state: the "privileged (CPL0)" bucket was CPL0 only on the first iteration.

## Sweep buckets (quick / `--full`)

Every form of the sweep lands in exactly one bucket (`at_main.cpp` `k_bucket_name`; the CSV `bucket` column, the report's bucket table and per-group columns; `Emulator\tools\isa\gen_instruction_table.py` reads the exact strings):

| bucket | meaning |
|---|---|
| `match` | the host CPU and Unicorn give the same architectural result in every iteration |
| `differs` | at least one iteration differs (the CSV `detail` column has the first one) |
| `unicorn-#UD (hw runs it)` | the host runs it, Unicorn raises #UD in every iteration |
| `host lacks + unicorn #UD` | #UD on both in every iteration and the host CPU does not have the instruction (e.g. every EVEX form on the i5-13600K, AMD FMA4/XOP, AVX-512 opmask VEX forms) |
| `invalid encoding, #UD on both` | (U930) #UD on both in every iteration on an instruction the host CPU has: an encoding the SDM makes invalid (F3 0F 38 F0/F1, which Capstone names MOVBE; VEX VSIB gathers whose destination, index and mask overlap) or #UD by definition (UD0/UD1/UD2; VMREAD outside VMX operation). "The host has it": the host's runtime CPUID for the form's Capstone ISA group (an EVEX form needs AVX512F or AVX10; MOVBE, VMREAD/VMWRITE and UD0/1/2, which Capstone tags only `base`, by mnemonic), or another form of the same mnemonic and class ran natively in the same run (with `--filter` / `--sample` only the forms run count). Before U930 these were part of `host lacks + unicorn #UD` |
| `host lacks, unicorn runs (needs SDM check)` | the host #UDs, Unicorn runs it: checked against SDM vectors instead (verified_forms.tsv) |
| `not native-safe, unicorn runs (needs SDM check)` / `not native-safe, unicorn #UD` | the form cannot run natively (reason in `detail`); Unicorn's outcome |
| `privileged (CPL0; CPL3 check in Phase 3)` | a CPL0 instruction: Unicorn runs it at CPL0, never natively; the CPL3 fault (vs the host) is a Phase 3 item (D6). Was `privileged (CPL0 in raw unicorn; Phase 2 CPL3)` before U930 |
| `harness error` | the snippet could not be built or run (fails the run) |
| `known deviation (docs/quirks.md)` / `known deviation not observed (matches)` | a form listed in `Emulator\data\alltest_known_deviations.tsv` that differs / matches |

## Prepared native runs (U850)

The sweep runs a form on the host CPU only when nothing it does can leave our regions (CODE / DATA / MEM at 0x30000000) or touch host state. Most forms get there with the random state alone (memory operands on RSI / R14 = MEM + 8000h, RDI = MEM + 9000h). The rest get a prepared state on top of the random one (`at_universe.hpp` `prepare_native`, `pin_base`, `patch_moffs`; applied by `at_main.cpp` `apply_setup`, identically for both engines), and Unicorn runs them at CPL3 with the Windows GDT (`cpl=3`, as the host):

| forms | prepared |
|---|---|
| memory operand on another GPR base (the map-0F 38h/3Ah forms the sweep finds with the tail byte 5Bh as ModRM = `[rbx+0]`: AES*, SHA*, ADCX/ADOX, CRC32, MOVBE, MOVDIRI, MOVDIR64B, GF2P8*, PBLENDW, PEXTRD/Q, PMAXUW, PABSD, PHSUBD, WRSS) | the base register := MEM + 8000h (an index other than RCX := 0) |
| `MOV moffs` (A0–A3) | the 8-byte absolute address (0x5BC0 from the tail bytes, never mapped) is rewritten to MEM + 8000h; the form text shows the new address |
| Jcc, JRCXZ, LOOP/LOOPE/LOOPNE, JMP/CALL rel32, XBEGIN, INT3, INT1 | branch layout (`program::ctl`): the snippet sits between two 100h-byte pads, the rest of CODE is HLT (F4h). A taken branch stops at its target: CPL3 HLT is #GP(0) with RIP = the HLT, in both engines |
| JMP/CALL r64 / m64, RET [imm16], RETF/RETFQ [imm16], far JMP/CALL m16:xx | the register, the memory operand or the stack slot at RSP holds LAND = CODE + 8000h (HLT); far forms the selector 33h (the host's CS); RSP := STACK_TOP − 100h for the forms that pop. A 16-bit RETF / m16:16 target (8000h) is below 64 KiB, never mapped under Windows: #PF in both |
| PUSH, PUSHF, POP, POPF, ENTER, LEAVE | RSP := STACK_TOP − 100h for the forms that pop; POPF: TF cleared in the popped image (a trap in the epilogue), every other RFLAGS bit but RF compared; LEAVE: RBP := STACK_TOP − 100h; ENTER with a nesting level > 0: RBP inside the test stack; PUSH Sreg: outcome only (the selector is the environment's) |
| LSS | the selector after the offset := 2Bh (the host's own SS, as in `cases_fixes2.txt`) |

For a branch-layout form a fault anywhere but the prologue and epilogue belongs to the snippet (native: the vectored handler, only on the running thread while the snippet runs; Unicorn: the INTR / unmapped hooks), and the comparison adds the fault RIP (not for INT3 / INT1: UC_HOOK_INTR reports the next RIP, Windows the INT3) and the whole state at that fault. The test stack is compared from the lower of input and output RSP when nothing faulted (an RSP below the stack, ENTER 5BC0h, compares all of it).

Forms that stay out, with the reason in the CSV `detail` column: SYSCALL / SYSENTER (a real kernel entry), INT n (Windows' IDT decides natively; Unicorn delivers INT n to UC_HOOK_INTR without an IDT), WRFSBASE / WRGSBASE (the host thread's FS/GS base; GS base = the TEB), LFS / LGS (the host thread's FS/GS selector and base), XBEGIN when the host has RTM. WRUSSD/WRUSSQ are CPL0-only (SDM: #GP(0) at CPL > 0) and counted as privileged.

## Run-to-run measurement (U1050)

`--hw-repeat N` runs each hardware case's native snippet N times (the first run is the one compared with Unicorn, so verdicts and summary lines are those of a normal run) and prints, after the case, every distinct host outcome with its count: the vector, for an access violation the Windows access type and address (CR2), the RIP offset and every field that changed. Each run is labelled with the core class it ran on:

- **This machine's Windows is a VMware guest** (VMware BIOS and 440BX board, 8 vCPUs as 2 sockets x 4 cores, CPUID.1:ECX[31] hypervisor bit hidden, CPUID.1AH reading 0; checked 2026-10-09). Its vCPUs run on whichever physical core of the i5-13600K the host schedules: a P-core (Raptor Cove) or an E-core (Gracemont). The guest cannot read the core type, and pinning a vCPU does not pin a physical core.
- So each run is classified by a timing probe taken just before and just after it: a dependent chain of four "add rax, 1" plus dec/jnz (our own 25 bytes, 1024 iterations, the lowest of 3 tries) in TSC ticks per iteration. On this host the values fall in two separate bands: 0.6-1.5 ticks (one iteration per clock: P-core) and 3.5-4.2 ticks (four clocks per iteration: E-core), with nothing between them (8 vCPUs x 2000 tries). The label is `[P]` / `[E]` when both probes agree, `[~]` when they disagree, `[?]` outside both bands, and `*` when the logical CPU number changed during the run. The probe is empirical for this host, not a CPU specification; on bare metal CPUID.1AH names the core type (printed at the start).
- `--hw-cpu SPEC` pins the native runs to logical CPUs (vCPUs here): a number or a comma list, `all` (rotate over every CPU of the process), `P` / `E` (the CPUs of that CPUID.1AH core type, bare metal only). Each outcome line lists the logical CPUs it was seen on (`cpus: n:count`).
- `--hw-load N` runs N busy threads (the probe's chain) beside the native runs, so the guest's vCPUs compete for the host's cores.

Use it for cases whose hardware result differs between runs: an outcome that follows the core class is an implementation difference between the two core types of the hybrid i5-13600K, not noise. Measured with it (2026-10-09, 2000 runs per case, 306 cases): the run-to-run differences of MASKMOVDQU, the MMX x87 state transition, FLD/FSTP m80 / FBLD / FBSTP across 0000_7FFF_FFFF_FFFFh and the unmasked #IS store all follow the core class (P-class runs with the P outcome 99.98%, E-class runs with the E outcome 97-98%; the rest are runs whose vCPU moved between the probe and the run).

**Probe measurement files (U1720-U1722, not gates, not in test_runner.ps1).** `Emulator\data\cases_probe_p1_hw.txt` (user-mode exception fidelity: the Windows access type of a faulting read-modify-write, MOV DR at CPL3, LAR/LSL), `cases_probe_p2_hw.txt` (the single-step side of the MOV SS / POP SS shadow; the debug-register items need DR support the harness does not have) and `cases_probe_p10_hw.txt` (anti-emulation probes: RPL026, BT135, BDF97, BT230/BT33/BT36, BT11/BT17/BT12, the Domas set, TF over CPUID/RDTSC, CPUID out-of-range leaves, SYSCALL with an invalid service number, the VMware-only backdoor port and pseudo-PMCs). Every line carries `# host state: measurement ...` / `# host state: VM-only ...`, so differences are counted per item; run them with `--hw-repeat 20` (`--guest --hw-cpu all` in the VMware guest, `--host [--host-core E] --cpuid <P/E profile> --hw-cpu P/E` on bare metal). What each line measures, the guest results and the harness needs: `notes\eread\P9_probe_snippets.md` (emulator tree).

## Quirks

`--quirks` and the UC_CTL_X86_HW_QUIRKS control are being removed (plan 1.G, pure SDM). Hardware cases where the i5-13600K deviates from the SDM are tagged `# known deviation: <name>` (documented in `docs\quirks.md`; the same tag marks the VMware-guest artifacts "PTWRITE hidden by the guest CPUID" and "HRESET hidden by the guest CPUID", which are not CPU deviations: the guest CPUID hides features the physical processor enumerates); host-state differences (RDRAND values, APIC ID, …) are tagged `# host state: <reason>`. Both are counted separately so every file reports 0 unexplained differences. **Stated differences (U1862, plan 1.F.13.c, G25 gap 2):** a tag may end with a bracket list of the fields it accepts, `# known deviation: <name> [mxcsr]`, `[fault mxcsr]`, `[dr6=0x1]` - the field names of the `uc vs hw:` line (`m` for any memory byte), `fault` (the vector differs), `dr6` or `dr6=MASK` (only those DR6 bits), `dbrip`, `dbcount`, `pfaccess`; a difference outside the list makes the line `DIFF (outside the tag's stated difference)` (counted as differing, with a `tag: not accepted` line naming the fields). A tag without a list still accepts any difference (all tags written before U1862; converting them is open, P21 LEFT). A native-side harness problem (debug-register thread error or note) is never accepted by a tag. **Native-only measurement lines (U1871, plan 1.F.13.f, user decision 2026-10-22 "Native-only tag"):** `# native only: measurement <name>` marks a measurement line whose Unicorn side cannot run (the SYSCALL line of `cases_probe_p10_hw.txt`: Unicorn has no OS, the OS path is Phase 3); the host CPU's result is printed (`[n] NATIVE ONLY`, `hw:`, the `--hw-repeat` outcomes), the Unicorn side is skipped on purpose and the line is counted as `native only: O` (a summary line plus one line per native-only case, never in `cases:`). The name must start with `measurement ` and the tag states no difference (else a bad tag: harness error); a native-side harness problem stays a harness error. A test.cmd suite must have no native-only line (test_runner.ps1), except the self-test `harness_selftest_native` (kind `nonly`: `case lines: 2, run: 1, native only: 1`); `harness_selftest_bad` lines 17-18 are the two bad forms. `cases_bdf97_hw.txt` and the VMware DR6.B0 lines of `cases_dbgfix_hw.txt` use stated tags. The quick / `--full` report's "Known deviations:" line counts the forms of `Emulator\data\alltest_known_deviations.tsv` in neutral wording, "hardware result differs from the SDM-modelled emulator result, documented in docs/quirks.md" (U1813; the list also holds the PTWRITE guest artifact); the suite `alltest_report_wording` (`Emulator\tools\check_alltest_report_wording.py`) checks that line in the quick run's report and in `Emulator\data\alltest_baseline\alltest_report.md`.

## Paired hardware cases (U614)

A hardware case `<host asm> ~~ <unicorn asm> | <inputs>` runs the first snippet on the host CPU and the second on Unicorn and compares the two results like any hardware case. `Emulator\data\cases_apx_core_hw.txt` uses it to run each instruction's legacy encoding on the i5-13600K against its REX2 encoding on Unicorn (`--apx`, no CPUID profile, which would hide APX); test.cmd's `:hw_apx` requires `differing: 0`.

## Exception error codes (U772)

In an expected-value case the fault token may carry the error code in parentheses: `#GP(0)`, `#SS(0)`, `#GP(0x30)`, `#CP(2)`, `#PF(0x6)` (a C literal). Unicorn's error code is read in the `UC_HOOK_INTR` callback with `UC_CTL_X86_EXCEPTION` (U770, `uc_ctl_get_x86_exception`: vector, error code, #PF linear address) and must then equal it; the `uc:` line prints it as `fault #13(0x0)`. Without parentheses only the vector is compared, as before. Exceptions without an error code (INT n, #UD, #DE, ...) never match a token with one, and neither does a #PF that Unicorn reports for memory it has not mapped (a Unicorn memory error, not an x86 exception: only a #PF from the page walk with CR0.PG = 1 has an error code). Hardware cases compare the vector only: the Windows exception record does not carry the CPU's error code. Example (`Emulator\data\cases_fix4.txt`):

```
mov rax, qword ptr [rsp+rcx] | rcx=0x00007FFFCFFEC0FC => #SS(0)
```

## Native exception vectors (U773)

The native engine maps the Windows exception record to a vector (`vector_of`, `at_engine.hpp`). An access violation is #GP when its address (ExceptionInformation[1]) is -1, #SS when ExceptionInformation[0] = 3 (Windows reports a stack fault, e.g. a non-canonical `[rsp+rcx]`, with access type 3 and address 0), else #PF (access type 0 read, 1 write, 8 execute, and the address). Checked on this machine (Windows 10 19044, i5-13600K) with our own snippets; `cases_fix4.txt` has the hardware #SS / #GP / #PF lines. Before U773 every #SS was reported as #PF (14).

## Debug registers and event lines (U1740-U1742)

A case may set the debug registers for its snippet, on both engines, from a normal (not elevated) prompt: input tokens `dr0=V` .. `dr3=V`, `dr6=V`, `dr7=V`. V is a C literal, `s+OFF` (the snippet's first byte + OFF; the snippet's address depends on the prologue) or `m+OFF` (MEM + OFF; `[rsi]` = `m+0x8000`). Example (`Emulator\data\cases_probe_p2dr_hw.txt`): `.byte 0x8e, 0x16; inc r8; inc r8; inc r8; nop | cpl=3 m+0x8000=2B00 dr0=m+0x8000 dr7=0x70401` (data read/write breakpoint on the MOV SS operand).

- **Native:** a debug-register case runs the thunk on a fresh thread of our own. The thread is created suspended; `SetThreadContext` with `CONTEXT_DEBUG_REGISTERS` writes DR0-DR3 / DR6 / DR7 before its first instruction (the documented way for a suspended thread; MOV DR is #GP at CPL3), `GetThreadContext` reads back what Windows keeps (it sanitizes DR7 and the addresses; printed as `dbg: hw thread after SetThreadContext`), then the thread runs on the calling thread's logical CPUs (`--hw-cpu` pins the caller) and is waited for (30 s, then terminated: our own snippet only). The values exist only in that thread and end with it: nothing else of the process or the system changes, no admin rights. The VEH records `CONTEXT.Dr6` of the #DB, `CONTEXT.EFlags` and the RIP. Windows loads a thread's debug registers only while it keeps an enabled breakpoint for it: with nothing enabled (DR7 = 400h) the read-back is all 0 and the #DB context has Dr6 = 0 (measured in the guest), so DR6 counts as a hardware value only when the read-back DR7 has an L bit; a case that wants DR6 of a single-step trap alone enables an unused write breakpoint (e.g. `dr0=m+0xF000 dr7=0x10401`). Windows keeps DR7 without bit 10 and without G bits (read-back `dr7=0x1` for 401h). Chosen over setting the registers from the VEH (an INT3 at the start whose handler writes `Dr7` into the context): that relies on `NtContinue` loading debug registers from a modified exception context; the suspended-thread path uses only documented calls and leaves the calling thread's registers untouched.
- **Unicorn:** `uc_reg_write` DR0-DR3 / DR6, then DR7 (U878 inserts the breakpoints), before the prologue; DR6 is read in the `UC_HOOK_INTR` callback of a #DB and after the run.
- **Safety (hardware cases):** every enabled breakpoint (DR7 Ln / Gn) must lie on the snippet's bytes or in MEM, which the prologue and epilogue never touch; otherwise the case is `not run` (counted in the summary, and since U1840 a harness error: exit status 1, not in `cases:`). I/O breakpoints are not run natively. On the debug-register thread a #DB at the first epilogue byte is the snippet's last instruction's trap; a #DB anywhere else outside the snippet (the thunk hit a breakpoint) is resumed with RF = 1 and DR7 = 0 and reported (`dbg: hw note`, the case differs). Every resume to the epilogue sets RF = 1 and DR7 = 0 on that thread; Unicorn writes DR7 = 0 when it resumes after an event (the compatibility-mode gate pushes onto the snippet's stack, which may be watched). A snippet that switches to compatibility mode must leave it or fault itself (the probe file ends such snippets with UD2).
- **Verdict:** a debug-register hardware case also compares the #DB RIP and DR6 (when both are known); the `dbg:` lines print the snippet bytes, the values set, Windows' read-back and Unicorn's DR6 after the run. Expected-value cases accept the tokens too (Unicorn only) and `dr6=V` after `=>` checks Unicorn's DR6 after the run.
- **Event lines (U1741):** `hw event:` / `uc event:` after the engines' lines - always for a debug-register case, for every case with `--events`: vector, RIP (`s+OFF`), the EFLAGS image with RF / TF (native: `CONTEXT.EFlags` of the exception, i.e. the image the CPU pushed as Windows hands it to the VEH; Unicorn: RFLAGS when the hook ran - Unicorn style delivery pushes no frame, so the pushed RF is not visible there), DR6 of a #DB with its bits named, and for a #PF the access type (native `ExceptionInformation[0]`: 0 read, 1 write = error code W, 8 execute; Unicorn the same encoding from the unmapped hook's `uc_mem_type`, `UC_MEM_WRITE_UNMAPPED` = W = 1) and address. Measurement output only: without `--events` and dr tokens nothing changes for the existing suites.
- **#DB count and DR6 mask (U1771):** `dbcount` keeps DR7 armed when the snippet's first event is resumed (native: the VEH leaves `CONTEXT.Dr7` as it is, RF = 1, TF = 0; Unicorn: no DR7 = 0 in the hook), so a #DB the engine still has pending is delivered; every #DB of the run is counted (native: on the debug-register thread, stray ones included; Unicorn: every `UC_HOOK_INTR` with vector 1) and the verdict adds `#DB count (hw N, uc M)` when they differ; a later event resumes with DR7 = 0 and does not replace the first event's record. The `dbg:` lines print both counts, `--hw-repeat` outcomes carry `dbs=N`. `dr6mask=V` compares DR6 as `(hw ^ uc) & V` (printed as `mask V`). Both need debug-register tokens. Used by the D-f lines of `cases_dbgfix_hw.txt` (U1772): one #DB for TF plus a data breakpoint, B0-B3 left out of the compare.
- Summary line (only with debug-register cases): `debug-register cases: N (not run natively: R, #DB without a hardware DR6 from Windows: X, harness errors / notes: H)`.
- Measurement file (U1742, not a gate, not in test_runner.ps1): `Emulator\data\cases_probe_p2dr_hw.txt` (G15 P2 a, b, c, e: instruction breakpoint after MOV SS / POP SS, data breakpoint on the MOV SS / POP SS operand, single-step with an instruction breakpoint on the next instruction, DR6 after MOV SS, RF through IRETQ, the EFLAGS image of #PF / #UD / #GP), every line tagged `# host state: measurement P2..`; run it with `--guest --hw-repeat 20 --hw-cpu all` (guest) or with the bare-host profiles.
- **#PF access type in the verdict (U1767):** every hardware case whose run faults with #PF on both engines also compares the access type (the error code W bit as above: native `ExceptionInformation[0]`, Unicorn the unmapped hook's `uc_mem_type`); a difference reads `#PF access (hw 1, uc 0)`. Before, only the vector, the state and (debug-register cases) the #DB RIP / DR6 were compared.
- Gate file (U1766, in test_runner.ps1): `Emulator\data\cases_dbgfix_hw.txt` - the P2 lines of the measurement file that the fixes U1760-U1764 made equal (instruction breakpoint after MOV SS / POP SS, data breakpoint held over the next instruction, single-step DR6 BS only, RF for one instruction) and the 25 P1a read-modify-write #PF lines (W = 1) with their read-only / write controls, without host-state tags; the P2e DR6 line and the EFLAGS-image lines stay measurement only.

## Native side under Intel SDE (U1040)

A second, labelled reference for the expected-value files (user decision 2026-10-09): results are **SDE-validated**, never hardware-validated, and the SDM wins any disagreement. SDE is never linked into or shipped with the emulator and only ever runs emu-alltest (our own generated snippets). Two passes, because Unicorn's own JIT under SDE's Pin runs at about one case per second:

1. `sde.exe -<cpu> [knobs] -- emu-alltest.exe --cases FILE <the suite's options> --expect-only --native-under-sde RESULTS`: only the native side of each expected-value line runs, on SDE's CPU; its result goes to RESULTS, one line per case line: `L <case line> <FNV-1a of the line> run <faulted> <vector> [OFF:HEX ...]` (the bytes of the state image that differ from the input state), `... skip <reason>` or `... error <message>`. The run refuses to start unless its parent process is `pin.exe` (sde.exe -> pin.exe -> the application; Pin's VM DLLs are not in the loader's module list) and prints the CPU SDE presents (vendor, signature, CPUID (7,0)/(7,1)/(0Dh,0)/(19h,0)/(1Eh,1)/(24h,0), XGETBV(0)), also written to RESULTS.
2. `emu-alltest.exe --cases FILE <the suite's options> --expect-only --sde-results RESULTS` (a normal run): each expected-value line runs on Unicorn and is checked against `=>` exactly as without the option (same verdict, same exit status), then Unicorn's result is compared with SDE's on the bytes the expectation checks (strict: every checked field; loose `=>!`: the listed ones) plus the fault vector: `sde:` (SDE's changes), `uc vs sde: AGREE` or `DISAGREE ... | exp vs sde: ...`. Summary: `sde cases: N, uc agrees with sde: A, uc disagrees with sde: D, exp agrees with sde: E, not checked: S, errors: X` and one `sde not checked: REASON: n` line per reason.

`Emulator\tools\sde_crosscheck.ps1 [-Sde <kit>\sde.exe] [-Lock <emulator>\buildlock.ps1]` (without `-Sde`: the kit under the sources root, see below) runs both passes for every expected-value suite of test.cmd, each with the SDE CPU that has its features, one step at a time (long files as `--shard K/N` blocks; with `-Lock` every step goes through the shared build lock).

- The native thunk moves ZMM0-31 / K0-7 when SDE's CPU has AVX-512 or AVX10 with XCR0[7:5,2:1] set, and APX R16-R31 when it has APX_F with XCR0[19]: the prologue's VINSERTI128 block and the epilogue's VEXTRACTI128 block jump to two stubs at CODE + E000h / E800h that do the same plus VMOVDQU64 / KMOVQ / REX2 MOV (encoded by the harness: Keystone rejects them) and jump back (same byte counts: the snippet and the epilogue keep their addresses). Without `--native-under-sde` nothing changes.
- Resume: SDE ends the whole process on some conditions (an AMX #UD it reports as "AMX Exception", an internal exception in its FP emulation, ...). Pass 1 marks each line `P <case line>` before it runs; a rerun with the same RESULTS keeps the finished lines, records a marked line without a result as `error SDE ended the process at this line` (pass 2 counts it as not checked) and goes on.
- Not checked (with the reason): ZMM/K or R16-R31 keys when SDE's CPU lacks that state; an input MXCSR with reserved bits (FXRSTOR64 #GP in the prologue); snippet bytes 0F 05 / 0F 34 (SYSCALL / SYSENTER), CD 29h / 2Bh-2Eh (INT n with a vector Windows lets CPL3 use: fast fail, callback return, assertion, debug service, system call; any other INT n is #GP), REX2 map-1 05h/34h/AEh, 0F AE /0-/3 with mod = 11 (RD/WR FS/GS BASE: SDE ends the process, `-fsgs_abort`). A plain byte scan, so a match inside an immediate also excludes the line.
- Also not run (U1041): a line that expects #XM from a snippet with a 62h (EVEX) byte. SDE 10.13.1 ends the process with an unhandled X87_INVALID_OPERATION inside its own sde-mix-mt.dll instead of delivering an unmasked SIMD exception of an instruction it emulates (all 258 such lines of cases_evex_m1.txt did, no other line did); SSE / AVX #XM lines run on the host CPU and are checked.
- What differs by construction (harness artefacts in a report): the native side runs at CPL3 under Windows (Unicorn's expected-value cases run at CPL0 unless `cpl=3`), with Windows' CR0 and SDE's XCR0 (not Unicorn's reset values); CPUID is SDE's; RDRAND is the host DRNG (not the seeded model); Windows reports #GP and #PF through the exception record (vector only, no error code). SDE runs natively whatever the i5-13600K has (SSE, AVX2, x87, ...), so for those instructions an SDE result is a host result.
- SDE 10.13.1 knobs the script uses: `-chip_check_die 0` (an instruction the chosen CPU lacks is logged, not fatal), `-emit_illegal_insts 0` (an invalid encoding raises #UD in the application instead of ending the process), `-align_checker_action warn` (SDE's alignment checker otherwise stops the process; with warn the misaligned access of an emulated instruction completes - SDE raises no #GP there, the SDM does), `-ptr_raise 1` (an emulated access to unmapped memory raises an access violation instead of ending the process), `-fp16_fast 0` (exact FP16 MXCSR updates).
- SDE 10.13.1 on this machine: its launcher starts `pind.exe` with an unquoted path, so a kit under a path with a space fails with "Create pind process failed with code 5". The default kit path (`E:\sources\sde-external-10.13.1-2026-07-28-win\sde.exe`) has no space and is used as is; a path with a space (`-Sde`, `--sde` or `NOVMP_SOURCES_ROOT`) is replaced by its 8.3 short path, and the tools stop with a clear message when the volume has no 8.3 name for it.

## Reference sources: NOVMP_SOURCES_ROOT (U1410-U1412)

The tools that read external reference material find it under one sources root: the environment variable `NOVMP_SOURCES_ROOT`, default `E:\sources` (the material moved there from `garbage\emulator\Intel docs` on 2026-10-13). Resolver: `Emulator\tools\docroot.py` (Python) and `docroot.ps1` (PowerShell, dot-sourced). A missing path stops the tool with the path, what was expected there and the variable to set; there is no fallback to the old location.

| Below the root | Used by | Override |
|---|---|---|
| `xed-main\datafiles` | `Emulator\tools\isa\gen_evex_tables.py` | — |
| `xed-main\datafiles\apx-f` | `gen_apx_map4_sweep.py` | first argument `XED_APX_DIR` |
| `asmjit\db\isa_x86.json` | `gen_evex_tables.py` | — |
| `sde-external-10.13.1-2026-07-28-win\sde.exe` | `Emulator\tools\sde_crosscheck.ps1`, `sde_rcp.py` | `-Sde` / `--sde` |
| `pin-sources` | (`docroot.pin_sources()` / `Get-NovmpPinSources`; no tool reads it yet) | — |

Example: `$env:NOVMP_SOURCES_ROOT = 'D:\refs'` before running a generator. `gen_evex_tables.py` still finds the Intel text in `garbage\emulator\intel_docs_text` (`--garbage`).

## Output

`[n] SAME|DIFF <line>` per case, then `cases: N, differing: M`; with expected-value cases a second line `expected-value cases: N, differing: M, errors: E, skipped: S`; then always (U1840) `case lines: L, run: N, harness errors: E (hardware H, expected-value X), skipped: S`. A case line of either kind that cannot be parsed, assembled, loaded or run natively (a debug-register line `not run`), and (U1860) a hardware line whose Unicorn run failed (`uc error: ...`, e.g. `uc_emu_start: ...`; the native result is still printed, without a verdict - e.g. the SYSCALL measurement line of `cases_probe_p10_hw.txt`, which Unicorn cannot run without an OS), is a **harness error**: `    ERROR: harness error (...)` under it, not counted in `cases:`, and a final `ERROR: ...` line (before U1840 such a hardware line was dropped silently: not counted, exit 0). U1859: the case file is read in binary mode (lines end at LF, one trailing CR removed: the rule of test_runner.ps1 and the host package's `expected_counts.txt`), so L really is every case line of the file - in text mode a Ctrl-Z byte ended the file and a CR CR LF line was not seen (G25 gap 1). U1871: a file with native-only lines prints `case lines: L, run: N, native only: O, harness errors: ...` and L = N + O + E + S. Exit status 1 when an expected-value case differs, on any harness error, or when L ≠ N + E + S (a line dropped without a count); hardware differences are reported (test.cmd's `hw` kind requires `differing: 0` and `cases: N` = the file's case lines, U1841).
