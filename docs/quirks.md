# i5-13600K deviations from the Intel SDM

**The emulator implements only the Intel SDM.** There is no switch that selects hardware behaviour (user decision 2026-10-08: "IF we do not need the Quirks for now please remove them"). The quirk mechanism (`UC_CTL_X86_HW_QUIRKS`, `UC_X86_QUIRK_*`, `emu-alltest --quirks`) was removed in ledger U531–U539; this file only documents where the host CPU (Intel Core i5-13600K, Raptor Lake, microcode 0x129) does something the SDM does not allow, so that hardware comparisons can tell a documented deviation from a bug. The hardware comparisons run in a VMware guest on that CPU; where the guest's virtualized CPUID, not the processor, explains a result, the entry is listed under "VMware-guest artifacts (not CPU deviations)" (U1476: PTWRITE without PT, HRESET without CPUID).

Where the SDM is silent or says "undefined", "reserved" or "implementation specific", following the hardware is not a deviation: those behaviours are listed at the end ("SDM undefined, our choice").

## How the harness treats a deviation

- Hardware case files (`emu-alltest --cases`, no `=>`): a case that hits a documented deviation ends with `# known deviation: NAME`, NAME being one of the headings below. Such a case is counted under "known deviations", never as "differing". A tagged case that matches the hardware is listed as "not observed" (stale tag, or a CPU that sometimes takes the SDM path). Summary: `cases: N, differing: D, known deviations: K, host state: H`.
- Differences that are not an SDM question but a different machine state on the host carry `# host state: REASON` and are counted apart (RDRAND/RDSEED values, the CPUID initial APIC ID, WRUSS under the host's CR4.CET = 1).
- `test.cmd` (`:hw_zero`) requires `differing: 0` for its hardware files, i.e. every difference is tagged.
- `emu-alltest` quick / `--full`: the forms in `Emulator/data/alltest_known_deviations.tsv` (form text → NAME) land in the bucket "known deviation (docs/quirks.md)" instead of "differs" / "unicorn-#UD", or in "known deviation not observed (matches)".
- `emu-uc72-risk` (R10/R11/R14/R17/R18): a difference that is exactly a documented deviation is printed as "known deviation (docs/quirks.md) NAME: n cases" and does not fail the run (`x87_known_deviation`).

## Deviations

### FCOMI/FUCOMI C1

- Behaviour: FCOMI, FCOMIP, FUCOMI, FUCOMIP and the FSW condition code C1.
- SDM: Vol2A FCOMI/FCOMIP/FUCOMI/FUCOMIP, "FPU Flags Affected: C1 Set to 0."
- Emulator: C1 = 0 (the original QEMU line, both builds).
- i5-13600K: C1 is left unchanged.
- Hardware cases: `Emulator/data/cases_quirks.txt` lines 9–11 (C1 = 1 before the compare); emu-uc72-risk R11 (26 cases: the scenarios with C1 preset to 1) and R18 (13612 cases; the FCOMI cases that also raise an unmasked #IA are counted under "x87 compare unmasked #IA condition codes").
- Ledger: U38 (quirk bit 0), removed in U531.

### CVTPI2PS m64 x87 transition

- Behaviour: CVTPI2PS xmm, m64 (memory source).
- SDM: Vol2A CVTPI2PS: "This instruction causes a transition from x87 FPU to MMX technology operation (that is, the x87 FPU top-of-stack pointer is set to 0 and the x87 FPU tag word is set to all 0s [valid]). If this instruction is executed while an x87 FPU floating-point exception is pending, the exception is handled before the CVTPI2PS instruction is executed." No exemption for the memory form (only CVTPI2PD xmm, m64 "does not cause a transition").
- Emulator: TOP = 0, all tags valid, pending unmasked x87 exception → #MF first.
- i5-13600K: no transition, no #MF for the m64 form (the MMX-register form transitions).
- Hardware cases: `cases_quirks.txt` line 13; `alltest_known_deviations.tsv` `cvtpi2ps xmm0, qword ptr [rsi]` (--full: x87 FTW differs in 5 of 6 iterations); emu-uc72-risk R10 (`cvtpi2ps xmm0, qword ptr [rcx]`, FSW TOP) and R14 (pending #MF: hardware runs, emulator #MF).
- Ledger: U44/U50 (quirk bit 1), removed in U532.

### FYL2XP1 below -1

- Behaviour: FYL2XP1 with a finite ST(0) = x < −1.
- SDM: Vol1 8.5.1.2, Table 8-10 "Invalid Arithmetic Operations and the Masked Responses to Them": "FYL2XP1: operand more negative than –1" → #IA; masked response "Return the QNaN floating-point indefinite value to the destination operand". #IA has priority over #D (Vol1 4.9.2).
- Emulator: #IA for every finite x < −1, also with y = ±0 / ±∞ (U432).
- i5-13600K: x is an ordinary operand: no #IA; result x itself with PE, ±0 / ±∞ (sign of x XOR y) for y = ±0 / ±∞, and a denormal y raises #D first (unmasked: nothing stored).
- Hardware cases: `cases_quirks.txt` lines 15–19; emu-uc72-risk R17 (special operands: 2376 of 29400 FYL2XP1 cases) and R18 (360 cases); `alltest_known_deviations.tsv` `fyl2xp1` (U931: the --full inputs since U931 reach x < −1 with ST(1) valid in 3 of 6 iterations; the earlier inputs never did).
- Ledger: U53/U432 (quirk bit 2), removed in U533.

### DPPD two NaN products

- Behaviour: (V)DPPD where both products are NaN and destination element 1 is selected.
- SDM: Vol2A DPPD Operation (DP_primitive): `Temp2 := Temp1[63:0] + Temp1[127:64]`, written to every selected element; with two NaN operands the SSE result is the first source operand (Vol1 4.8.3.5, Table 4-8), so both elements get product 0.
- Emulator: product 0 (quieted) in both elements.
- i5-13600K: element i := p[i] + p[i^1] (each element's own product is the first addend), so element 1 gets product 1. Repeatable (10 runs, 2026-10-08).
- Hardware cases: `cases_dp_nan.txt` 252 of 384 cases (tagged by `gen_cases_nan.py --dp-hw`, which evaluates both orders); `cases_quirks.txt` lines 24–25. The SDM model itself: `cases_dp_nan_sdm.txt` (876 expected-value cases).
- Ledger: U98 (quirk bit 4), removed in U535.

### REP 67h ECX=0 zero-extension

- Behaviour: REP/REPE/REPNE MOVS, STOS, LODS, CMPS, SCAS with a 32-bit address size (67H) in 64-bit mode and ECX = 0.
- SDM: Vol2B REP/REPE/REPZ/REPNE/REPNZ Operation: the address size selects ECX as CountReg, then `WHILE CountReg ≠ 0 DO … OD`: with ECX = 0 nothing is executed and no register is written.
- Emulator: nothing is written (the original QEMU code; the U60/U430 split is gone).
- i5-13600K: zero-extends RCX, RSI, RDI (MOVS), RCX, RDI (STOS), RCX (LODS, CMPS, SCAS). REP LODS takes the SDM path in about 4–5 % of the runs (hwcheck_gate1 case 6: 16 of 400 runs), so its tag can be reported "not observed". The rate depends on what runs on the other logical processors (U544, measured 2026-10-09, 200 runs of hwcheck_gate1 each): 8/200 serially with the pre-U540 emu-alltest, 7/200 serially with U540, 26/200 (13 %) with 8 copies side by side; so test.cmd runs hwcheck_gate1 and cases_quirks alone, before the parallel suites (U541).
- Hardware cases: `hwcheck_gate1.txt` lines 7–13; `cases_quirks.txt` lines 27–29.
- Ledger: U60/U430 (quirk bit 5), removed in U536.

### x87 compare unmasked #IA condition codes

- Behaviour: FCOM, FCOMP, FCOMPP, FUCOM, FUCOMP, FUCOMPP (and the aliases DC D0+i, DC D8+i, DE D0+i) and FCOMI, FCOMIP, FUCOMI, FUCOMIP when they raise #IA with FCW.IM = 0.
- SDM: Vol2A FCOM: "If the invalid-arithmetic-operand exception is unmasked, the condition code flags are not set"; FUCOM: "the condition code flags are set only if the exception is masked"; FCOMI: "the status flags in the EFLAGS register are set only if the exception is masked" (Operation: `IF FPUControlWord.IM = 1 THEN C3, C2, C0 := 111`).
- Emulator: C3/C2/C0 (FCOMI: ZF/PF/CF) unchanged.
- i5-13600K: sets them to "unordered" (111) anyway. (FTST and FICOM have no such condition in the SDM: 111 on both.)
- Hardware cases: `cases_quirks.txt` lines 32–37; `cases_x87_cmp_exc.txt` (216 tagged cases: FCOM/FCOMP/FCOMPP, FUCOM/FUCOMP/FUCOMPP, FCOMI/FCOMIP/FUCOMI/FUCOMIP, FCOM/FCOMP m32/m64 with an SNaN, QNaN (ordered forms) or unsupported operand and FCW.IM = 0; U861); emu-uc72-risk R18 (3494 cases: NaN operands with IM = 0).
- Ledger: U54/U431 (quirk bit 6), removed in U537.

### DPPS exception step grouping

- Behaviour: (V)DPPS with an unmasked SIMD floating-point exception.
- SDM: Vol2A DPPS Operation: DP_Primitive on each 128-bit half in turn, the handler invoked "if unmasked exception reported" after the products, after Temp2, after Temp3 and after Temp4; Exceptions: "Exceptions are determined separately for each add and multiply operation, in the order of their execution. Unmasked exceptions will leave the destination operands unchanged."
- Emulator: exactly that order (U446): a step with an unmasked exception raises #XM at once, later operations set no flags.
- i5-13600K: checks after all products (both halves of VDPPS ymm), after Temp2 and Temp3 together, after Temp4, so flags of operations the SDM would not reach yet are set (example: Temp2 exact tiny with UM = 0 and Temp3 inexact → UE and PE).
- Hardware cases: `cases_sse_exc.txt` 84 of 174028 cases (22 dpps, 62 vdpps ymm), tagged by `gen_cases_sse_exc.py` with `Emulator/tools/isa/dpps_steps.py` (an exact binary32 model of each multiply/add that evaluates both orders; the tagged set equals the set the old quirk bit changed).
- Ledger: U446 (quirk bit 7), removed in U538.

### DPPS two or more NaN products (measurement only)

- Behaviour: (V)DPPS with two or more NaN products in one dot product.
- SDM: DPPS Operation (DP_primitive) plus Table 4-8: the first NaN product in the order p0, p1, p2, p3 in every selected element. The emulator implements that (`cases_dp_nan_sdm.txt`).
- i5-13600K: not repeatable from run to run, so `cases_dpps_nan.txt` (492 cases) is a measurement file, not a gate. 40 runs on 2026-10-08:
  - 225 of the 492 cases changed result at least once.
  - Each run had 9–41 cases (2–8 %) that differed from the majority result, usually in short runs of neighbouring cases.
  - Elements 0 and 2 never varied. Element 0 always gets the first NaN in the order (1, 0, 3, 2) and element 2 in the order (3, 2, 1, 0).
  - Elements 1 and 3 usually follow the orders (0, 1, 2, 3) and (2, 3, 0, 1). In about 10 % of the affected results the order within one pair is swapped.
  - The majority rule is t[j] := p[j^1] + p[j], element i := t[i] + t[i^2].

### LOCK PREFETCHW

- Behaviour: PREFETCHW m8 (0F 0D /1) with a LOCK prefix; also the register form 0F 0D /1 mod=11b (a NOP, U77).
- SDM: Vol2B PREFETCHW, Protected/Real-Address/Virtual-8086/Compatibility/64-Bit Mode Exceptions: "#UD If the LOCK prefix is used." Vol2A LOCK: PREFETCHW is not in the list of lockable instructions.
- Emulator: #UD (U457, the old decoder's LOCK table).
- i5-13600K: runs it (no #UD, no fault) for /1 with a memory or register operand; the other 0F 0D encodings (/0, /2, /7, register /0) with LOCK are #UD, as is LOCK PREFETCHNTA (0F 18 /0).
- Hardware cases: `cases_backport_t1.txt` lines 197, 199 (the /0, /2, /7 lines next to them match); `cases_fix4.txt` lines 149–150 (all 16 LOCK forms /0–/7 memory and register are on lines 147–162, the 14 others match; lines 163–178 the forms without LOCK, all NOPs on both).
- Ledger: U457.

### SYSRET at CPL3 in compatibility mode

- Behaviour: SYSRET (0F 07, also with REX.W) executed at CPL3 in compatibility mode (IA32_EFER.LMA = 1, CS.L = 0) with IA32_EFER.SCE = 1 (Windows).
- SDM: Vol2B SYSRET Operation: `IF (CS.L ≠ 1) or (IA32_EFER.LMA ≠ 1) or (IA32_EFER.SCE ≠ 1) or (CR4.FRED = 1) THEN #UD; FI; IF (CPL ≠ 0) THEN #GP(0); FI;` and Compatibility Mode Exceptions: "#UD The SYSRET instruction is not recognized in compatibility mode."
- Emulator: #UD (U460: Intel SYSCALL/SYSRET only in 64-bit mode).
- i5-13600K: #GP(0) (Windows reports STATUS_PRIVILEGED_INSTRUCTION): the CPL check is made first. In 64-bit mode at CPL3 both give #GP(0).
- Hardware cases: `cases_backport_t1.txt` lines 308–309 (64-bit mode lines 305–306: #GP(0) on both).
- Ledger: U460.

### MASKMOVDQU-AC

- Behaviour: MASKMOVDQU (66 0F F7) with the destination [RDI] not 8-byte aligned, CR0.AM = 1, EFLAGS.AC = 1, CPL = 3.
- SDM: Vol2B MASKMOVDQU, "Other Exceptions: See Table 2-21, Exceptions Type 4" - type 4 has no #AC row (Vol2A Table 2-21, unlike types 3/5/6); Vol3A 7.15 names the 128-bit unaligned moves whose #AC "may or may not" be generated (MOVDQU, MOVUPS, MOVUPD, LDDQU), not MASKMOVDQU.
- Emulator: no #AC (the selected bytes are stored).
- i5-13600K: #AC (STATUS_DATATYPE_MISALIGNMENT) for [RDI] at 4 mod 8.
- Hardware cases: `Emulator/data/cases_ac_hw.txt` line 240 (MASKMOVQ, whose #AC row the SDM has, Vol3B Table 25-8, matches: lines 237-238).
- Ledger: U834.

### SxDT-STR-SMSW-NO-AC

- Behaviour: SGDT, SIDT, SLDT m16, STR m16 and SMSW m16 at CPL3 (Windows leaves CR4.UMIP = 0) with CR0.AM = 1, EFLAGS.AC = 1 and a misaligned operand.
- SDM: Vol2B SGDT / SIDT / SLDT / STR / SMSW, Protected Mode Exceptions: "#AC(0) If alignment checking is enabled and an unaligned memory reference is made while CPL = 3"; Vol3A 7.15: "Storing the contents of the GDTR, IDTR, LDTR, or task register in memory while at privilege level 3 can generate an alignment violation"; Table 7-7: "GDTR, IDTR, LDTR, or Task Register Contents" 4, word 2.
- Emulator: #AC(0) when the operand address is not a multiple of 4 (SGDT, SIDT, SLDT, STR) or 2 (SMSW).
- i5-13600K: no #AC at any offset (+1, +2, +4, +6 tried); the stores are made.
- Hardware cases: `Emulator/data/cases_ac_hw.txt` lines 241-246.
- Ledger: U834.
### REP CMPS/SCAS flags at a fault

- Behaviour: REPE/REPNE CMPS or SCAS (any width) whose second or a later iteration faults (here: the next element on a not-present page), so the instruction stops after one or more completed iterations.
- SDM: Vol2B REP/REPE/REPZ/REPNE/REPNZ Operation: `WHILE CountReg ≠ 0 DO Service pending interrupts (if any); Execute associated string instruction; CountReg := (CountReg – 1); ... IF (Repeat prefix is REPZ or REPE) and (ZF = 0) ... THEN exit WHILE loop; FI; OD;` — each iteration executes CMPS/SCAS, which set the status flags ("The CF, OF, SF, ZF, AF, and PF flags are set according to the temporary result of the comparison"); "A repeating string operation can be suspended by an exception or interrupt ... the ECX register has the value it held following the last successful iteration". So the faulting state has the flags of the last completed iteration (the faulting iteration changes nothing, Vol3A 6.5).
- Emulator: the flags of the last completed iteration with RCX/RSI/RDI as after it, RIP at the instruction (U774; also what memory hooks see during an iteration: the flags of the iteration before).
- i5-13600K: RCX/RSI/RDI as after the completed iterations, but RFLAGS as before the instruction (e.g. `cmp r8, r9; repe cmpsq` with an equal first pair and a not-present second one: RFLAGS 297h, the CMP's, not 246h).
- Hardware cases: `cases_fix4.txt` lines 54–67 (REPE/REPNE CMPSQ, CMPSD, SCASQ, SCASB after nine different flag setters); the four lines after them (no fault) match.
- Ledger: U774.

### MMX #PF x87 transition (P-core)

- Behaviour: an MMX instruction whose memory access takes #PF (here: a not-present page) while the x87 state is not already the MMX state (TOP != 0 or a tag not valid): MOVD m32, mm / MOVQ m64, mm / MOVNTQ m64, mm stores after FLD1 (TOP = 7), and MASKMOVQ.
- SDM: Vol3A 7.5 (Vol3A 6.5 before rev. 092): "When a fault is reported, the processor restores the machine state to the state prior to the beginning of execution of the faulting instruction"; the x87-to-MMX transition (Vol1 9.5.1: TOP = 0, all tags valid) belongs to the faulting instruction, so TOP and the tag word keep their values. Vol2B MASKMOVQ: "Transition from x87 FPU to MMX technology state will occur" (for the executed instruction).
- Emulator: no transition when the access faults (#PF, #GP, #SS, #AC, or memory Unicorn has not mapped): TOP and the tag word unchanged (U834 for #AC, U873 for the rest); the transition is made after the access, MASKMOVQ's after its store.
- i5-13600K: the reference is a VMware guest whose vCPUs run on the hybrid CPU's P-cores or E-cores (runtorun report 2026-10-09, `--hw-repeat`, U1050). P-cores: `fld1; movq [unmapped], mm0` (also MOVD / MOVNTQ) sets TOP = 0 with the tags unchanged; MASKMOVQ #PF (any mask, nothing stored) makes the full transition (TOP = 0, tags valid). E-cores: neither changes TOP or the tags (the SDM). MMX loads (MOVQ, PADDB, PSHUFW, ...) and stores from the default state make no transition on either core type (33,655/33,655 P-class runs, 1968/1985 E-class).
- Hardware cases: none in gate files (core-dependent). `cases_fix5.txt` U873 section: hardware lines for the loads (after FLD1) and the stores from the default state (both core types agree); MASKMOVQ as expected-value lines. Measurement: runtorun report section 3.
- Ledger: U873.

### BSF/BSR PF

- Behaviour: BSF / BSR with a non-zero source: the PF flag (the other flags agree).
- SDM: 325383-092 Vol2A BSF / BSR "Flags Affected": "The ZF flag is set to 1 if the source operand is 0; otherwise, the ZF flag is cleared. The PF flag is set to 1 if the number of bits set in the source operand is even; otherwise, it is cleared. The CF, OF, SF, and AF flags are all cleared." (footnote: "On some older processors, the CF, OF, SF, AF, and PF flags are unmodified"). Revisions 080, 084 and 086 said "The CF, OF, SF, AF, and PF flags are undefined"; the definition is new in 092 (or 090/091, not held).
- Emulator: SDM 092 (U1121): CF = OF = SF = AF = 0, ZF = (source = 0), PF = 1 when the population count of the whole source operand (16/32/64 bits) is even. Before: QEMU's SF = the source's sign bit, PF = the parity of the source's low byte.
- i5-13600K: ZF, CF, OF, SF and AF as the SDM, whatever the input flags; PF = the parity of the low byte of the result, the bit index (for example `bsf ax, cx` with CX = 8000h: index 15, PF = 1, where the SDM's count of 1 gives PF = 0). P-cores and E-cores agree: `emu-alltest --hw-repeat 400` (U1050), idle and with `--hw-load 7`, 94 cases, 75200 runs, one outcome per case; 66 of the cases ran on both core classes. For a zero source both rules give PF = 1 (`cases_bsf_zero_hw.txt`).
- Hardware cases: `Emulator/data/cases_bsf_flags_hw.txt` (the 66 cases with P- and E-core runs; 41 tagged `# known deviation: BSF/BSR PF`, the 25 where both rules give the same PF untagged). The `--full` sweep does not see it: Capstone still marks the BSF/BSR flags but ZF undefined (the pre-092 text), so the sweep compares only ZF.
- Ledger: U1121.

| CPUID.(14H,0):EBX[4] PTWRITE | 1 (EBX = 0000005FH) | 0 (leaf 14H all zero) |
| CPUID.(07H,1):EAX[22] HRESET | 1 (EAX = 00400810H) | 0 (EAX = 00000810H) |

### PTWRITE without PT

- Classification: VMware-guest artifact (2026-10-14), formerly listed as a deviation.
- Behaviour: PTWRITE r/m32, r/m64 (F3 [REX.W] 0F AE /4) on a CPU whose CPUID.(EAX=14H,ECX=0):EBX[4] = 0.
- SDM: Vol2B PTWRITE, Protected Mode Exceptions: "#UD If CPUID.14H.00H:EBX.PTWRITE[4] = 0."
- Emulator: #UD (the fork has no Intel PT; leaf 14H is 0 on every model and on the i5-13600K profile). The #UD comes before the memory operand is accessed.
- VMware guest on the i5-13600K (guest leaf 14H all zero; the physical CPU reports CPUID.(14H,0):EBX[4] = 1, table above): executes it: the operand is read (#PF/#GP as usual), nothing else happens; LOCK and 66H are #UD.
- Hardware cases (run in the guest): `cases_quirks.txt` lines 21–22; `alltest_known_deviations.tsv` `ptwrite eax`, `ptwrite dword ptr [rsi]`, `ptwrite rax`, `ptwrite qword ptr [rsi]` (--full: hardware runs, emulator #UD).
- Ledger: U80 (quirk bit 3), removed in U534; reclassified U1476.

### HRESET without CPUID

- Classification: VMware-guest artifact (2026-10-14), formerly listed as a deviation.
- Behaviour: HRESET imm8 (F3 0F 3A F0 C0 ib) on a CPU whose CPUID.(EAX=07H,ECX=1):EAX[22] (HRESET) = 0.
- SDM: Vol2A HRESET, Protected Mode Exceptions: "#UD If CPUID.07H.01H:EAX.HRESET[22] = 0."
- Emulator: the MAX model reports HRESET (U804) and executes it; with the i5-13600K CPUID profile (strict, bit 22 = 0) it is #UD.
- VMware guest on the i5-13600K (bit 22 = 0 as Windows in the guest reports it; the physical CPU reports CPUID.(07H,1):EAX[22] = 1, table above): decodes it; at CPL3 #GP(0) (the CPL check of an implemented HRESET). Other ModRM bytes than C0 are #UD on both.
- Hardware cases (run in the guest): `cases_sysins_hw.txt` (the two HRESET lines with ModRM C0, CPL3).
- Ledger: U804 (no quirk bit; tag only); reclassified U1476.

## Emulator environment choices (OS-preconfigured state, not architectural RESET)

Unicorn starts a guest the way an operating system leaves a thread, not the way a processor leaves power-up or RESET. These are deliberate choices of the execution environment, not CPU-vs-SDM deviations and not "SDM undefined" choices; they carry no case tag.

### XCR0 at engine start (U120 / U370 / U1225; documented U1440, user decision A18 2026-10-14)

- **Architectural RESET.** SDM 093 Vol3A 2.6 p. 2-23: "After reset, all bits (except bit 0) in XCR0 are cleared to zero; XCR0[0] is set to 1." Table 12-1 (Contd.) p. 12-3: XCR0 = 1H at power-up and at RESET, unchanged by INIT. Vol1 13.3 pp. 13-5 / 13-6 gives the same per component ("XCR0[1] is 0 coming out of RESET", ... "XCR0[18:17] have value 00b coming out of RESET"). So after RESET XCR0 = **1H** (x87 only) and every other bit is 0; CR4 is 0 as well (Table 12-1), so XGETBV / XSETBV are #UD until system software sets CR4.OSXSAVE and then enables components with XSETBV.
- **Emulator default (deliberate environment choice).** `x86_cpu_reset` (cpu.c, U120 / U370) and `reg_reset` (unicorn.c, U67) start with CR4.OSFXSR | OSXMMEXCPT | OSXSAVE set when CPUID.01H:ECX.XSAVE = 1 and with XCR0 = **every user state component the configured CPU model enumerates in CPUID.(EAX=0DH,ECX=0):EDX:EAX**, i.e. the state an OS leaves after XSETBV of everything the CPU offers. It is derived per model and per opt-in, not from "what every OS uses" (Windows on the i5-13600K runs with 7H although that CPU enumerates 207H, `docs/emu-alltest.md`): bit 0 always; bit 1 with CPUID.01H:EDX.SSE; bit 2 with CPUID.01H:ECX.AVX; bits 4:3 with CPUID.(7,0):EBX.MPX; bits 7:5 with AVX512F (`UC_CTL_X86_AVX512`, any non-zero mask) or AVX10 (`UC_CTL_X86_AVX10`); bit 9 with CPUID.(7,0):ECX.PKU; bits 18:17 with CPUID.(7,0):EDX.AMX_TILE (`UC_CTL_X86_AMX`); bit 19 with CPUID.(7,1):EDX.APX_F (`UC_CTL_X86_APX`, which withdraws MPX, U610) - `x86_ext_save_areas` / `x86_cpu_esa_supported`, limited to `CPUID_XSTATE_XCR0_MASK`. Supervisor components (CET 12:11 in IA32_XSS) are never in XCR0.
- **Valid for the model by construction and by test.** One CPUID bit feeds each pair or group (MPX 4:3, AVX-512 7:5, AMX 18:17) and every AVX-capable model has SSE, so the default obeys every XSETBV rule of Vol1 13.3 / Vol3A 2.6 (bit 0 set; AVX only with SSE; MPX both or neither; AVX-512 all of 7:5 or none and only with 2:1; AMX both or neither; no reserved or supervisor bit) and equals CPUID.(0DH,0):EDX:EAX ("if and only if CPUID.0DH.00H:EAX[i] = 1"). `test_x86_xc_default_xcr0_models` checks every row below: the value, CR4.OSXSAVE = CPUID.01H:ECX.OSXSAVE = 1, XCR0 = CPUID.(0DH,0), the rules, XGETBV, XSETBV accepting both the default and the RESET value 1H, AVX running with the default and #UD with 1H.

- **With a CPUID profile.** No profile or a non-strict one: the model's value above. - **Open (reported 2026-10-14, not changed).** Decision A18 expects "the strict architectural profile" to start with XCR0 = 1H and to need XSETBV before relying on more state. The emulator has no such profile: `UC_CTL_X86_CPUID_STRICT` only restricts CPUID-visible features, and a strict profile starts with the narrowed OS value (207H with the i5-13600K profile; `test_x86_xc_arch_reset_vs_default` locks this current behaviour). A change needs a decision first (the expected-value suites run with strict profiles take this reset value).

## IA-32e IDT delivery: error code of the 64-bit code-segment check (user decision 2026-10-14)

IA-32e-mode IDT event delivery (the interrupted code in 64-bit or compatibility mode) through an interrupt or trap gate whose selector references a code segment that is not a 64-bit code segment (CS.L = 0, or CS.L = 1 with CS.D = 1). A specification reading, not a CPU deviation: the i5-13600K's IDT cannot be changed from user mode, so it is neither hardware- nor SDE-validated and carries no hardware-case tag. SDM = 325462-093 (page numbers as in the single-volume PDFs 253668-093 Vol3A and 253666-093 Vol2A).

- What is reported (explicit): Vol3A 7.14.1 "64-Bit Mode IDT", p. 7-21: "The target code segment referenced by the interrupt gate must be a 64-bit code segment (CS.L = 1, CS.D = 0). If the target is not a 64-bit code segment, a general-protection exception (#GP) is generated with the IDT vector number reported as the error code." Vol3A Event 13 "Exception Error Code", p. 7-45, lists "IDT vector number" among the sources of an error code, and "General Protection Exception in 64-bit Mode" (same page) lists "If the code segment descriptor pointed to by the selector in the 64-bit gate doesn't have the L-bit set and the D-bit clear." Vol2A INT n/INTO/INT3/INT1, Compatibility Mode Exceptions, p. 3-481 (64-Bit Mode Exceptions: "Same exceptions as in compatibility mode"): "#GP(error_code) ... If the descriptor pointed to by the gate selector doesn't have the L-bit set, or has both the L-bit and D-bit set."
- How the vector is encoded (inferred from 7.13): Vol3A 7.13 "Error Code", pp. 7-19 / 7-20, defines one format for error codes that refer to a selector or an IDT vector: the index field (bits 15:3), IDT (bit 1: "When set, indicates that the index portion of the error code refers to a gate descriptor in the IDT") and EXT (bit 0). An IDT vector number in that format is index = vector, IDT = 1 - the encoding the Vol2A INT n Operation uses for the other checks of the IDT entry, error_code(vector_number,1,EXT) = (vector << 3) | 2 | EXT (pseudofunction p. 3-469; IA-32e-MODE p. 3-471; ledger U1400).
- EXT: the origin of the event being delivered, never set unconditionally (Vol2A p. 3-469: "if that event is a software interrupt (INT n, INT3, or INTO), EXT is 0; otherwise (including INT1), EXT is 1"; Vol3A 7.13 p. 7-19 and its footnote 1 for INT1). INT n / INT3 / INTO: 0; exceptions, INT1, external interrupts, NMI: 1 (ledger U1401).
- Emulator: #GP((vector << 3) | 2 | EXT), e.g. INT 40h 202H, a SELF IPI 40h 203H, #UD 33H, INT FFh 7FAH. Only this check changed: the other code-segment checks of the gate keep the selector-based codes of Vol2A TRAP-OR-INTERRUPT-GATE, p. 3-472 (null selector #GP(EXT); beyond the table limit, not a code segment, DPL > CPL #GP(selector | EXT); not present #NP(selector | EXT); ledger U1402). The check keeps its place after the DPL and present checks (the SDM lists the conditions without an order between them; combinations are not tested). A #GP raised here while a contributory exception (#DE, #TS, #NP, #SS, #GP) is delivered becomes #DF(0) as before.
- Discrepancy (recorded, not grounds to override the SDM): upstream QEMU 11.1 `E:\sources\qemu\target\i386\tcg\seg_helper.c` lines 1023-1024 (do_interrupt64: `raise_exception_err(env, EXCP0D_GPF, selector & 0xfffc)`) and Bochs `E:\sources\Bochs\bochs\cpu\exception.cc` lines 131-135 (long_mode_int: `exception(BX_GP_EXCEPTION, cs_selector.value & 0xfffc)`, EXT added at line 953) report the destination code-segment selector. The original-QEMU build (`__Use_Original_Qemu=1`) keeps the selector.
- Code / tests: `seg_helper.c` do_interrupt64 (`idt_vector_error_code(intno, ext)`); unit tests `test_x86_i6_cs_mode64` (CS 38H L = 0 D = 1, 40H L = 1 D = 1, 48H L = 0 D = 0; interrupt and trap gates; INT 40h / FFh / 06h / 01h, INT3, SELF IPI 40h / FFh, #UD, INT1, NMI; #DE → #DF(0); INT 0Dh → #GP(6AH) through the same gate → #DF(0)) and `test_x86_i6_cs_sel64` (the selector-based checks unchanged through both gate types).
- Ledger: U1422.

## IA-32e IDT delivery: 16-bit interrupt / trap gates (06H / 07H) - SDM-open, provisional policy (user decision 2026-10-15)

IA-32e-mode IDT event delivery (the interrupted code in 64-bit or compatibility mode) through an IDT entry whose type is 06H (16-bit interrupt gate) or 07H (16-bit trap gate). **SDM-open**: an unresolved inconsistency of the Intel specification, present since the first IA-32e document (2004) and unchanged in SDM 093 (September 2026). The emulator's behaviour is a **provisional policy**, not an Intel requirement. Not a CPU deviation: there is **no hardware evidence** (the i5-13600K's IDT cannot be changed from user mode), no SDE run and no erratum; no hardware-case tag. Evidence and per-revision table: `emulator\notes\eread\G5_gate0607_final.md`.

- Rule A - #GP(0) (section text). Intel 64-bit Extension Technology Software Developer's Guide 300834-001 (Rev 1.00, February 2004) §1.6.10.1 "Gate Descriptor Format" (PDF p. 50, printed 1-34; 300834-002, June 2004: PDF p. 46) → SDM Vol3A §5.14.1 (253668 revs 015-030), §6.14.1 (031-084), §7.14.1 "64-Bit Mode IDT" (085-093; 093: p. 7-21): "If a reference is made to a 16-bit interrupt or trap gate (06H or 07H), a general-protection exception (#GP(0)) is generated." The sentence is unchanged in every revision; no change document (252046-001 to -085 as present locally) touches or explains it.
- Rule B - an error code naming the vector (instruction text). Vol2A INT n/INTO/INT3/INT1 (253666): (1) the exception list classifies "not a 64-bit interrupt/trap gate" under #GP(selector) (300834-001 p. 2-264, PDF p. 318; SDM 015-035), #GP(error_code) from rev 036, and from rev 090 explicitly apart from the #GP(0) group (093 Compatibility Mode Exceptions p. 3-481: "If the vector points to a descriptor which is not a 64-bit interrupt gate or a 64-bit trap gate"; 64-Bit Mode Exceptions refer to it); (2) the IA-32e-MODE pseudocode (from rev 015): "selected IDT descriptor is not an interrupt-, or trap-gate type THEN #GP(...)" with the error code vector×16 + 2 + EXT (015-032), (vector « 3) + 2 + EXT (033-035; change document 252046-026, December 2009) and error_code(vector_number,1,EXT) = (vector << 3) | 2 | EXT (036-093; change document 252046-029, September 2010; 093 p. 3-471, pseudofunction and EXT p. 3-469). Context that supports reading 06H / 07H as "not an interrupt- or trap-gate type": Vol3A Table 3-2 (093 p. 3-14), IA-32e column: types 6 and 7 "Reserved"; Vol2A pseudocode comment from rev 035 "IF IDT gate is 16-bit (* implies IA32_EFER.LMA = 0 *)" (093 p. 3-478).
- Why open: both rules coexist since 2004; Intel corrected the pseudocode error code twice without touching the #GP(0) sentence; no passage gives one precedence; no erratum or hardware result settles it. Applying the pseudocode's "not an interrupt- or trap-gate type" to 06H / 07H is a reading (strongly supported by Table 3-2 and the LMA = 0 comment), the #GP(0) sentence is explicit.
- Provisional policy (kept, no code change): **#GP((vector << 3) | 2 | EXT)** - the same form as every other IDT entry that is not a 64-bit interrupt or trap gate (U1400 / U1401), checked after the IDT limit and before the DPL and present checks (so a not-present 06H / 07H gate is #GP, not #NP). Examples: INT 44h 222H, INT 45h 22AH, INT3 1AH, INT1 0BH, INT 01h 0AH, #UD 33H, SELF IPI 61h 30BH, NMI 13H, INTO in compatibility mode 22H; a contributory exception (#DE) whose delivery meets such a gate, and a #GP whose own gate 13 is 06H / 07H, become #DF(0). EXT as U1401. Reasons: three of Intel's descriptions (exception lists, pseudocode, Table 3-2 / LMA = 0 context) agree against one sentence; uniform with the other invalid types. Upstream QEMU 11.1 (`do_interrupt64`: #GP(intno * 8 + 2), no EXT), Bochs (`long_mode_int`: #GP(vector * 8 + 2), EXT added by `exception()`) and AMD APM Vol 3 r3.38 READ_IDT (#GP(vector * 8 + 2); a separate vendor) agree - precedent only, not evidence of Intel behaviour. If #GP(0) is ever adopted, the narrower form is #GP(0 | EXT) (Vol3A 7.13 has allowed a null error code to carry EXT since rev 036).
- Observable by software: a guest #GP handler (and a VMX hypervisor's VM-exit interruption / IDT-vectoring error-code fields) sees e.g. 222H / 33H instead of 0H / 1H.
- Switch point: `unicorn\qemu\target\i386\seg_helper.c` do_interrupt64, the `default:` case of the gate-type switch (`raise_exception_err(env, EXCP0D_GPF, idt_vector_error_code(intno, ext))`, U1400 / U1401); a policy change would add a `case 6: case 7:` there. Tests: `test_x86_idterr_gate16_64` (expected code in `ig2_gate16_ec`, one edit for a policy switch), separate from `test_x86_idterr_gate_types64` (types 01H-05H, 08H-0DH and S = 1 descriptors, 0EH / 0FH as controls) and from the code-segment checks (`test_x86_idterr_cs64`, `test_x86_i6_cs_mode64`, `test_x86_i6_cs_sel64`).
- Related but separate: the same §7.14.1 rule for a gate whose target code segment is not a 64-bit code segment (IDT vector number as the error code) is decided on its own (U1422, section above).
- Ledger: U1423 (policy record and tests; the behaviour itself is U1400 / U1401).

## IA-32e IDT delivery: frame pushes into non-canonical space - documented policy (user decision 2026-10-15)

IA-32e-mode IDT event delivery whose new RSP is canonical but whose 40- or 48-byte frame reaches non-canonical space (RSP is aligned down to 16 bytes first, Vol3A 7.14.2: with 4-level paging an RSP from FFFF_8000_0000_0000H to FFFF_8000_0000_002FH; with CR4.LA57 = 1 from FF00_0000_0000_0000H to FF00_0000_0000_002FH). A specification reading, not a CPU deviation: the i5-13600K's IDT cannot be changed from user mode (no hardware or SDE result, no hardware-case tag). SDM = 325462-093; audit `emulator\notes\eread\C2_framecross_audit.md`.

- What the SDM specifies (class 1): such a push raises **#SS**, not #GP. Vol2A INT n/INTO/INT3/INT1, Compatibility Mode Exceptions, p. 3-482 (64-Bit Mode Exceptions: "Same exceptions as in compatibility mode"; wording since 090): "#SS(error_code) If an ordinary stack access would use an address that is not canonical relative to the current paging mode or cause a LASS violation." Revisions 015-089 named each push ("If a push of the old SS selector, ESP, EFLAGS, CS selector, EIP, or error code is in non-canonical space on a stack switch (either CPL change or no-CPL with IST)"; without a stack switch the EFLAGS, CS, EIP and error-code pushes). Vol1 3.3.7.1 and Vol3A 4.5.1 (p. 4-5: stack accesses get #SS, "a null error code") say the same in general terms. Error code: EXT with a null selector (class 2, from Vol3A 7.13 p. 7-20 "all bits are clear except possibly EXT", the #SS(EXT) of the new-RSP check, Vol3A 8.3.4 for FRED and Vol3C 29.6.1.1 for VMX injection): 0 for INT n / INT3 / INTO, 1 otherwise (INT1 included, U1401).
- What the SDM does not specify: whether the pushes made before the failing one stay in memory, and in which order a #PF on the canonical part of the frame and the #SS on the non-canonical part are reported (Vol3A 7.9 p. 7-10: Table 7-2 "does not specify the prioritization of faults that arise during instruction execution or event delivery"; only the 64-bit call gate checks its whole frame up front, Vol2A CALL p. 3-132, and INT n has no such check).
- **Emulator policy (documented, per-push order):** every push is checked just before its store, in the order of the Operation pseudocode (SS, RSP, RFLAGS, CS, RIP, error code). The first non-canonical slot raises #SS(EXT); **the pushes before it stay written**; a #PF on a canonical slot above the boundary is reported first because that slot is pushed first. Nothing is loaded (RSP, SS, CS, RIP, RFLAGS and CPL keep the interrupted values; the shadow-stack steps of CET are not reached). Examples (4-level paging): RSP FFFF_8000_0000_0010H - SS and RSP written at ...0008H / ...0000H, #SS(EXT) at the RFLAGS push; RSP FFFF_8000_0000_0020H - four slots written, #SS(EXT) at the RIP push; RSP FFFF_8000_0000_0000H - nothing written; RSP FFFF_8000_0000_0010H with the page at FFFF_8000_0000_0000H not present - #PF (CR2 FFFF_8000_0000_0008H), not #SS.
- Order against the other delivery checks (class 1, pseudocode Vol2A pp. 3-474 / 3-478): #TS(EXT) and #SS(EXT) for the TSS RSPn / ISTn (U1402), #SS(EXT) for a non-canonical new RSP (U1420) and #GP(EXT) for a non-canonical gate offset (U1421) come first. #SS and #GP are both contributory, so the double-fault escalation is the same as with stock QEMU's #GP(0): a crossing frame during the delivery of #DE, #TS, #NP, #SS, #GP or #PF is #DF(0), and a crossing #DF frame is a shutdown (`UC_ERR_EXCEPTION` with IDT delivery).
- Canonical as the MMU data path: after LAM masking (Vol3A 4.4 / 4.5.1; it cannot change the result for a frame below a canonical RSP), 48 / 57 bits by CR4.LA57. No check under `UC_TLB_VIRTUAL` (Unicorn's virtual TLB has no canonical rule, U42). LASS is not modelled. Upstream QEMU and the original-QEMU build (`__Use_Original_Qemu=1`) store the push and raise #GP(0) from the MMU.
- Code / tests: `seg_helper.c` idt64_pushq / do_interrupt64; unit tests `test_x86_ig3_frame_cross64`, `_paging64`, `_df64`, `_order64`, `_la57_64`, `_vmx64`, `_tlbvirt64`.
- Ledger: U1424.
