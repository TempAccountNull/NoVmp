# WAITPKG timing probe for the BARE HOST (plan 1.J.55, ledger U1602, agent waitpkg, 2026-10-17). Not a gate file: it
# measured what the emulator models as its environment wake period (docs/quirks.md "WAITPKG wait duration", U1622) - how long a TPAUSE /
# UMWAIT with a far deadline really waits under Windows, and whether it ends by the OS time limit (CF = 1,
# IA32_UMWAIT_CONTROL[31:2] != 0) or by another wake event such as the clock interrupt (CF = 0). That tells whether
# Windows programs IA32_UMWAIT_CONTROL (a CPL0 MSR that user mode cannot read), the --host environment value
# (docs/quirks.md "IA32_UMWAIT_CONTROL at engine start").
# Each line: t0 = RDTSC; deadline = t0 + 2^40 (minutes away); TPAUSE / UMWAIT; R10 = CF; R11 = bit index of the highest
# set bit of the elapsed TSC ticks (BSR: 16 = 65536..131071 ticks); every other changed register is zeroed. The
# emulator's result (U1620-U1622: the TSC jumps to the end of the wait, here the 2^21-tick wake event, engine-start limit 0)
# is R10 = 0, R11 = 15H (the unarmed UMWAIT line: no wait, R11 = its own JIT time) - the bare host's most frequent outcome
# (run 20261018_232017_native-host: R10 = 0, R11 = 14H / 15H) - so each line carries "# host state" and never counts as differing.
# Run on the bare host only (on the VMware guest every line is #UD):
#   emu-alltest --cases Emulator\data\cases_waitpkg_probe_hw.txt --host --strict --xcr0 7 --hw-cpu P --hw-repeat 50
#   emu-alltest --cases Emulator\data\cases_waitpkg_probe_hw.txt --host --host-core E --strict --xcr0 7 --hw-cpu E --hw-repeat 50
# Report the "host outcomes" lists (R10 / R11 per outcome, with counts). Expected: if Windows sets a limit L, CF = 1 and
# R11 = BSR(L) in most runs; if it sets none, CF = 0 and R11 = the clock-interrupt period (about 2^24..2^26 ticks).
# Statements (U1896; U1900-U1901, plan 1.F.13.h, G28 A1 / A3; host statements checked against the native AND the Unicorn result
# of the SAME bare-host run, notes\eread\P24_tagsh.md): the Unicorn R11 of the last line (UMWAIT without UMONITOR: no wait, SDM)
# is a timing value too - BSR of Unicorn's own elapsed TSC ticks between its two RDTSCs (its TSC is the host's TSC). All data

# U1910 (plan 1.F.13.i, G29-3) - the far lines 30 / 31 / 33, Unicorn side. The wait model (U1620 / U1622, misc_helper.c
# helper_waitpkg): with no OS limit and a deadline 2^40 ticks away the TSC jumps by W = 2^21 ticks (the environment wake)
# inside TPAUSE / the armed UMWAIT; every other tick between the two RDTSCs is host time d >= 0 spent by the thread outside
# the wait (the no-wait tail of line 35: the same instructions without the jump). So R11 = BSR(W + d): 15H for d < 2^21,
# 16H for 2^21 <= d < 3 * 2^21, 17H only from d >= 3 * 2^21 - a class 15H..16H(timing) on both core types (the Unicorn run
# is not pinned). Data: VMware guest 2026-10-23 (--host / --host-core E, 3820 far-line samples: 1800 of this file's lines
# 30 / 31 / 33 + 2020 copies of line 30) 15H x3820; G29 420 samples 15H x419 / 16H x1 (line 30: d >= 2^21 once, a
# descheduled thread); P24 234 guest runs 15H; bare host v3a P / E 6 x 15H. The no-wait tail d itself (guest single tries
# 4040: at most 3B738H < 2^18; line 35 2620 samples at most 12H but one negative count) stays far below 2^21, so a wait that did not happen gives
# at most 14H and is refused by the lower bound 15H. A 17H needs a delay of 3 * 2^21 ticks between two RDTSCs (not seen in
# 4474 guest samples). The exact W is not this line's job: cases_waitpkg_host.txt (U1911) checks that the smallest of 16
# waits is W + less than 8000H ticks (a doubled wake gives 17H here but fails test.cmd there). Hardware side 0xD..0x15:
# 15H was observed natively on every far line (20261018 P and E, v3a P) - it pairs with a Unicorn 16H (an equal 15H on
